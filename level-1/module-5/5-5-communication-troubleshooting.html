Module 5 · BMS Communication Protocols

5.5 Communication troubleshooting

Week 4 · Day 24About 10 minPage 5 of 5✓ Done
After this page you can
  • Troubleshoot communication faults layer by layer, from the cable up.
  • Choose the right tool for each layer.
  • Recognise the symptoms of the most common Modbus, MS/TP and BACnet/IP faults.
  • Isolate a faulty device or segment on a bus quickly.
Warm-up · 3 quick questions from earlier pages (2 min)
  1. Priorities 8 and 16 both hold values. Which wins?
    from 5.4 BACnet MS/TP and BACnet/IP
    Show answer
    Priority 8 — the lowest number that is not null.
  2. What does exception 02 mean?
    from 5.3 Modbus RTU and Modbus TCP
    Show answer
    Illegal data address — the register does not exist on that device.
  3. Which UDP port does BACnet/IP use by default?
    from 5.2 IP address, subnet mask, device ID and baud rate
    Show answer
    47808 (0xBAC0).
In one line

Fix communication faults from the bottom up: prove the wiring, then the settings, then the protocol details, then the application — and split the network in half until the fault has nowhere left to hide.

?Why it matters

Communication faults look the same on the screen — “offline”, “?”, frozen values — whatever the cause. Guessing at settings wastes hours. A fixed order of checks, and the right tool at each step, turns them into routine jobs.

Step by step

  1. Define the scope. One point, one device, one segment, or everything? Shared symptoms point to shared causes.
  2. Physical. Power on? Cable continuous, right polarity, right topology? Termination and bias correct? IP link lights on?
  3. Settings. Address, baud, parity, stop bits; IP, mask, gateway; device instance, MAC, Max_Master, network numbers. Compare with the numbering plan.
  4. Talk to it directly. Connect a laptop tool straight to the device. If the tool works and the BMS does not, the problem is in the BMS configuration.
  5. Protocol details. Function code, register address and offset, data type, word order, scaling; BACnet object type and instance.
  6. Application. Poll rate and timeouts, too many points, overrides in the priority array.
  7. Divide and conquer a bus: disconnect half; whichever half still fails holds the fault. Repeat.

Write it down

Record what you checked and the readings — A–B resistance, settings, error counts. Communication faults often return, and a log turns the next visit into a five-minute job.

Follow AHU-01

Worked example: the AHU-01 graphic shows the VFD's kW as “?”. Hard-wired points are fine, so only the Modbus link is affected. (1) Physical: A–B resistance with power off = 60 Ω; the drive's RS485 LED never flashes. (2) Settings: the drive was replaced last week and its parameters are at factory default — 9600 8N1, address 1 — while the controller uses 19200 8E1. Set the drive to 19200 8E1, and the values return. Add the drive's parameters to the as-built records so the next replacement goes faster.

⚒On site

  • Ask what changed recently — a replaced device, a firmware update, new IT equipment. Most faults follow a change.
  • Check the device's diagnostics page or error counters before swapping hardware.
  • Keep a known-good USB–RS485 adapter and a laptop with Modbus and BACnet tools in your kit.
  • Never reconfigure a working device's address “to see if it helps” without writing down the original.

AKey terms

Bottom-up troubleshooting
Checking physical layer first, then settings, protocol and application.
Divide and conquer
Splitting a network in halves to locate a fault.
Modbus master tool
Software that sends Modbus requests directly to a device (e.g. Modbus Poll, QModMaster).
BACnet explorer
Software that discovers and reads BACnet devices (e.g. YABE).
Wireshark
Network packet capture tool that decodes BACnet/IP and Modbus TCP.
Error counters
Device statistics of CRC errors, timeouts and token faults.

✓Check yourself

Try each one before opening the answer.

Fault scenario · what would you do?

On an MS/TP floor bus, all 20 FCUs went offline at 10:00. An electrician installed one new FCU controller at 09:55. Power is fine everywhere. What is the most likely cause?

A single device with a mismatched baud rate or duplicate MAC can upset token passing for the whole MS/TP segment. Disconnect the new device: if the others return, configure it correctly before reconnecting.

  1. List the four layers in bottom-up order.

    Show answer
    Physical → settings → protocol/data → application.

  2. Your laptop Modbus tool reads the device perfectly, but the BMS shows timeouts. Where is the fault?

    Show answer
    In the BMS side: its port settings, driver configuration, addresses or polling.

  3. Ping works but BACnet/IP discovery fails. Name two causes.

    Show answer
    UDP 47808 blocked by a firewall; device on another subnet without a BBMD; non-standard BACnet port.

  4. How does divide and conquer work on a bus?

    Show answer
    Disconnect half of the bus; the half that still shows the fault contains it. Repeat until one device or cable section is left.

  5. What should you ask first when a working system stops communicating?

    Show answer
    What changed — replaced devices, firmware, IT equipment, new devices on the bus.
